# Petals test release notes

Branch: `test-release`, version `0.1.0-test.1`. This is a test build only.
Existing notes and rooms are not migrated or rewritten. All new fields are
optional with backward compatible defaults, legacy base64 photos still
render, and old rooms still open.

## What changed

### Auth, session, room entry
- Session persistence: Firebase Auth persistence is set in `client/src/firebase.ts` (IndexedDB on Capacitor, browser local persistence on web). Firestore uses a persistent local cache, so notes stay readable offline and edits queue.
- Email/password signup and login added in `AuthPage.tsx`, with validation, friendly error messages, and forgot password. Google sign-in is unchanged.
- Display name is no longer overwritten on login (`useAuth.ts` only sets it on first creation). `SettingsPage.tsx` syncs the name input when the profile loads.
- Room entry: 6-char code validation, clear errors, loading state. QR generate (`RoomQr.tsx`, payload `petals://room/XXXXXX`) and QR scan (`QrScanner.tsx`, html5-qrcode, camera fallback to manual code) in AuthPage join and in Settings.

### Photos, placement, video
- Photo placement is now a fixed logical canvas, 360 wide by 5600 tall (`client/src/utils/canvasCoords.ts`). X is percent of width, Y is logical px. Legacy px/percent data is normalised on read only, never rewritten. Insert uses the centre of the visible card, not the viewport. Drag and resize divide by `--notebook-zoom` consistently in `Polaroid.tsx` and `StickerCanvas.tsx`.
- Smart compressor (`client/src/utils/imageCompressor.ts`): WebP, start 1920px quality 0.86, target 700KB, steps down to 0.72 then shrinks 15 percent, max 5 tries, strips EXIF/GPS, 400px thumbnail.
- Storage photos: new photos go to B2 as a transient relay plus the subcollection `rooms/{roomId}/notes/{noteId}/photos/{photoId}` (`usePhotos.ts`, 30 per page, `loadMore`). Legacy `Note.photos` still renders alongside, deduped by id. `PhotosPage.tsx` shows note photos and chat photos/videos in date groups, thumbnails first, with search and Save to Gallery on each tile. View-once never appears there.
- Video prototype, short clips only, in Chat only (2026-11-17): 60 seconds, 720p, 50MB max, poster via canvas, resumable upload with progress, WiFi-only option. See `docs/VIDEO_RESEARCH.md`. No ffmpeg.wasm in the app. Videos were removed from notes on 2026-11-17, see "No videos on notes" below; the video limits and validation now live only in `ChatPage.tsx` / `ChatInput.tsx`.

### Messaging fixes, 2026-11-17 (audit before tonight)
- Retry no longer writes local-only flags to Firestore: `handleRetry` in `ChatPage.tsx` used to spread the optimistic copy into `sendMessage`, which wrote `temp: true` / `failed` onto the real message doc. It now builds a clean payload with only real message fields.
- Rapid sends work: the Send button used to be disabled by a global `sending` flag while any message was in flight, so fast consecutive messages were blocked. Sending is now per-message only (each optimistic bubble tracks Sending / Sent / Seen / Retry itself), and the button is disabled only on empty text. The `sending` prop is gone from `ChatInput.tsx`.
- Double haptic on send removed: `ChatInput` and `ChatPage` both fired the success haptic for one text send. Only `ChatInput` fires it now.
- Typing indicator expiry: the "Partner is typing…" pill could stick on screen when no new snapshot arrived, because it was only re-evaluated on render. ChatPage now re-renders on a 2s tick so the 5s typing window expires.
- Double-tap burst only when liking: double-tapping an already-liked message unlikes it, but the heart burst still played. The burst now only fires when the message was not already liked.
- Swipe-to-reply no longer also triggers a tap: the click fired right after a swipe could open the lightbox or like the message. The tap after a swipe is now suppressed.
- Deleted media messages are really gone: `deleteMessage` in `useMessages.ts` used to keep `mediaUrl` / `thumbUrl` on the doc, so a deleted photo/video was still downloadable from its old URL. Delete now clears both URLs as well as the text.
- Rules checked and unchanged: `firestore.rules` already allows room members to create messages (senderUid must match), update them (reactions, viewedBy, cachedBy, deletedAt), and write `lastReadAt` / `chatTyping` on the room doc via the room update rule. No rule change was needed for any of this.
- Still relies on Firestore's persistent local cache for offline text: text sends queue in Firestore and sync when back online; media has the explicit IndexedDB queue in `localStore.ts` that flushes on reconnect.

### Local-first cache, client-side primary, transient relay
- `client/src/utils/localStore.ts`: light IndexedDB wrapper, no new dependency. Cache-first reads for notes and messages, cached rooms and profiles, thumbnails and compressed photos as Blobs, short video clips up to 50MB cached when opened (bigger clips keep only a thumbnail), total media cache 500MB, LRU eviction by last viewed, favourites/pinned media is never evicted, effective budget is the smaller of 500MB and 60 percent of `navigator.storage.estimate()` quota.
- Client-side primary: the full compressed photo or video is stored on the uploader's device first, at upload time (`saveLocalMedia` in localStore, `saveHiddenMedia` in mediaStore), so the uploader never re-downloads their own media. The partner's device stores its own full copy the first time it opens the file.
- Why Storage cannot be fully removed for a 2-person shared app: a photo stored only on device A cannot be seen on device B unless there is a transfer path. Local-only would break the shared notebook, the partner would never see it. WebRTC peer-to-peer needs both devices online at the same time, needs a signalling server anyway, and published WebRTC telemetry puts TURN relay fallback at about 15-20 percent of real-world attempts, higher on mobile networks, so a meaningful share of transfers would go through a relay server anyway. So B2 stays, but only as a transient relay: the full file is uploaded, the partner downloads and caches it locally, `cachedBy` on the photo/message records who has it, and once both room members are in `cachedBy`, the full file is deleted from B2 (`relayDeleted: true`, `deleteRelayFullFile` in b2Storage, `markCached` in usePhotos/useMessages). The thumbnail stays in B2 permanently, about 60-80KB per photo, so the grid still loads.
- What server usage actually becomes, before archiving: long-term B2 is only thumbnails, about 80KB per photo, so the 10 GB free tier holds about 125,000 thumbnails. Full files, about 700KB compressed, or up to 50MB for a clip, sit in B2 only between upload and the partner's first open. Firestore still holds all metadata, notes, messages and thumbnails' URLs. Downloads drop to thumbnails plus one full download per device per photo, instead of a download on every open. After the 30-day archive (next section), archived full files stay on B2 long-term, so that thumbnails-only figure no longer holds once items start expiring.
- Honest limits of client-side-only: IndexedDB in a Capacitor WebView is best-effort storage, it can be evicted under storage pressure and is gone if the user clears app data or uninstalls. `navigator.storage.persist()` is requested, best effort, it is not a guarantee. On Android the hidden files are real files in app-specific external storage, which survives app updates but not uninstall. If the relay file is deleted after both devices cached it, and a device then clears its cache, that device cannot get the full file back from the server, only its thumbnail, unless the item was archived to Storage by the 30-day archive job, in which case the archived copy is the way back. Originals are never stored: the local copy is the compressed 700KB WebP or the compressed 720p clip, not the 3-5MB original. At 700KB, 500MB holds about 700 full photos; at original 3-5MB it would hold only 100-160, which is why compression stays.
- Update-check result is cached for 24 hours. QR and room data are cached locally (room id was already in localStorage).
- Offline queue: Firestore queues document writes itself. Media uploads do not queue in Firestore, so Chat media is queued explicitly in IndexedDB and flushed when back online. Notes media uses the same B2 upload path; if B2 fails offline, the editor falls back to legacy base64 capped at 6 photos so the note doc cannot blow up.
- Sync status: offline badge in App, online/offline and queued count in Settings. Listeners unsubscribe when a tab closes because lazy pages unmount on tab switch; the App-level message listener for notifications is the only always-on listener, and it reads only the latest message.
- Limits: the cache is per device, not shared. Clearing it never deletes server data, but after a relay file was deleted it also cannot rebuild that full file. A device with a small storage quota will evict sooner. View-once media is cached like other media on the viewing device in this test build, and the file stays in hidden storage after viewing, see the view-once section.
- Clear cache in Settings, which also shows cache size (bytes used of 500MB, items, pinned count, device quota).

### 30-day archive to server (replaces the wipe)
- Revised rule, 2026-11-17: after 30 days without being opened, a full photo/video in hidden nomedia storage is NOT wiped forever. It is stored on the server instead: `client/src/utils/mediaArchive.ts` uploads it to B2 at `rooms/{roomId}/archived/{mediaId}.webp` (photo) or `.mp4` (video), verifies the upload by checking the download URL and that the stored size matches the uploaded blob, and only then deletes the local nomedia/IndexedDB copy. The Firestore doc is marked `serverStored: true`, `archivedAt`, `archivedUrl`, `archivedPath`, `localExpired: true`, and its media URL is pointed at the archived copy. The thumbnail stays, and Saved to Gallery copies are untouched.
- The job runs in App.tsx on launch, at most once a day, and once a day while the app stays open. It does nothing offline. Any failure leaves the local copy in place, so the next run can retry it. Settings shows the rule in plain text, how many items have been archived, the last check time, and a manual "Archive expired media now" button.
- Re-downloading: an archived item shows its thumbnail with "Stored on server - tap to download again" in Photos, Chat, the note Polaroid, and the Lightbox. Tapping it re-downloads the full file into nomedia storage, clears `localExpired`, and resets the 30-day clock. The server copy stays as the long-term backup.
- Exempt, never archived: thumbnails, pinned/favourite media, view-once media (uploading those back would defeat view-once), legacy base64 photos that live inside a note doc array (no photo subcollection doc to update), and anything whose room/doc cannot be resolved from the local metadata or its stored path. The relay cleanup in `markCached` (usePhotos/useMessages) never deletes an archived full file, even once both members have cached it.
- Storage cost, stated plainly: archived full files now stay on B2 long-term, about 700KB per compressed photo, up to 50MB per short clip, so server storage grows instead of staying thumbnails-only. At 700KB a photo, 5GB holds about 7,000 archived photos on top of thumbnails; videos are far heavier, about 100 clips at 50MB. The archived copy is never auto-deleted from B2. Deleting the note photo or chat message through the app deletes its current B2 file, including the archived copy, because deletePhoto/deleteMessage delete the current `storagePath`.

### Hidden storage and Save to Gallery
- Auto-downloaded photos and videos go to hidden app-private storage, never to Pictures/DCIM, and never trigger MediaScanner, so Gallery apps do not index them. On Android that is external app-specific storage, `Android/data/com.hi.petals/files/Petals/`, Capacitor Filesystem `Directory.External`, with a `.nomedia` file in the folder. It is deliberately NOT internal `/data/data` storage, so a file manager navigating to that exact path can see the files without root. MediaStore does not scan `Android/data` at all, and the `.nomedia` file is a second layer. On web, blobs live in IndexedDB, which has no file path and is hidden from the device gallery by definition.
- `client/src/utils/mediaStore.ts` is the module for this, with a native plugin `client/android/app/src/main/java/com/hi/petals/PetalsFilesPlugin.java` (registered in MainActivity). The plugin writes the Gallery copy through MediaStore, Pictures/Petals for photos and Movies/Petals for videos, and opens the hidden folder in the system Files app. `@capacitor/filesystem` 8.1.5 was added for the hidden files. Note: Filesystem `Directory.ExternalStorage` was not used for saving, it is not accessible on Android 11 or newer; MediaStore is the correct path on modern Android.
- Save to Gallery: a clear Save to Gallery button on each photo/video in the Lightbox, on each chat bubble with media, and on each Photos grid tile. On tap it copies the file to the visible Gallery folder and shows a toast, Saved to gallery. Copy is the default: the hidden Petals copy stays, the gallery copy is the visible one. Settings has a Move toggle, off by default, which deletes the hidden copy after a successful save. On web there is no Gallery, so Save to Gallery downloads the file instead.
- Settings toggles: Auto-download media, on by default; Auto-download on mobile data, off by default, so the default is WiFi only; and the Move toggle above. When auto-download is off or the user is on mobile data with WiFi-only on, full files are not fetched in the background, thumbnails still load and the file still plays or opens from the server when tapped.
- Settings shows the exact on-device path, `Android/data/com.hi.petals/files/Petals/`, and a Show in Files button that opens that folder in the Files app. If the Files app cannot be opened directly, the button copies the path so it can be pasted into a file manager. On web, Settings says plainly there is no file path and Save to Gallery is the way to get a real file.
- Answer to the question behind this: yes, you can still search for hidden media, inside Petals, and no, not in the phone Gallery or Files search. See the next section.

### In-app search for hidden media
- Hidden means hidden from Gallery, not from Petals. Gallery and Files search cannot find these files, because they are in an unscanned folder with `.nomedia`. Petals finds them because it knows each file by id and keeps its metadata in Firestore and in the local IndexedDB index, and search runs over that metadata, never by scanning the file system.
- PhotosPage has a search field and All / Photos / Videos filters. It matches note title, date (for example 17 Nov 2026) and photo or video, from metadata only. ChatPage has a search field that matches message text, sender name, date and photo or video. A viewed view-once item stays hidden even if it matches a search.
- Settings explains this in plain words: hidden from Gallery, not from Petals, and Save to Gallery is what makes a photo appear in Gallery search.

### Updates and CI
- Full in-app update flow, no browser (`client/src/utils/updateCheck.ts`, `UpdateBanner.tsx`, `client/android/app/src/main/java/com/hi/petals/PetalsUpdatePlugin.java`): the app checks the GitHub releases list from inside the app, shows an Update available banner, downloads the APK asset inside the app with a progress bar, then fires the Android install intent for the downloaded file. Android 8+ needs "install unknown apps" allowed for Petals first; when it is off the flow opens that settings screen instead of failing. Settings has a manual Check for updates button with a status line (up to date / no releases yet / rate limited / offline) and the same download/install controls. Dismissing a version keeps it dismissed until a newer release appears. On web there is no install intent, so Download just saves the APK file.
- Version source of truth is now `client/package.json` (0.1.0-test.1): `vite.config.ts` reads it for `__APP_VERSION__`, and `android/app/build.gradle` reads it for `versionName`, so the web bundle and the native app always report the same version. On Android the native versionName from the plugin is preferred when available. Previously the three disagreed: package.json said 0.1.0-test.1, vite.config.ts hardcoded it separately, and build.gradle said versionName "1.0".
- Comparison is real semver, not string equality: 0.1.0 is newer than 0.1.0-test.1, and 0.1.0-test.10 is newer than 0.1.0-test.2. The check uses the releases LIST endpoint, not /releases/latest, because /latest only returns full releases and test tags like v0.1.0-test.1 are prereleases, so /latest would 404 even when a test release exists. Drafts are skipped. A 404/empty list is now reported as "No releases published yet" instead of silently doing nothing, a 403 is reported as a GitHub rate limit, and being offline is reported as offline. The result is cached for a day; a manual check always goes to the network.
- Live fact, 2026-11-17: the repo has NO releases at all yet (GET /releases returns []), so the check reports no-release until a tag is pushed. The download/install half cannot be proven end to end until a release with an APK exists.
- `.github/workflows/ci.yml`: tsc, lint, build on push/PR to main and test-release.
- `.github/workflows/android-release.yml`: on tag `v*` and manual dispatch, builds the web app, runs `cap sync android`, builds a debug APK with Gradle, uploads it as an artifact, and attaches it to the GitHub release on tags.

## How to test each feature
- Login: sign up with email, sign in with email, reset password, sign in with Google. Close and reopen the app, you should stay signed in.
- Room: create a room, copy the code, show the QR in Settings, scan it from a second device or browser, join with the code.
- Photos: add a photo in a note, check it appears in the same place on a second device, drag it, resize it, add a second photo. Add a photo to an old note with legacy photos and check the old ones still show.

## Known limits
- Chat media is stored under `rooms/{roomId}/__chat__/{id}` in B2; the signer Worker validates that key pattern and checks room membership before minting any URL. After both members cache a chat or note photo, the full file is deleted from B2 and only the thumbnail remains; a device that clears its cache after that cannot get the full file back.
- The native PetalsFiles plugin (MediaStore save, open folder) is Java in the Android project and was not compiled here; it needs a device or emulator Gradle build to prove it, `npx cap sync android` only registers the Filesystem plugin and copies web assets. If the plugin call fails on a device, Save to Gallery falls back to a Documents write, and Show in Files falls back to copying the path.
- The native PetalsUpdate plugin (APK download + install intent) is also Java and was not compiled here, for the same Gradle reason. Its JS side degrades gracefully: if the plugin is missing, the check falls back to the baked-in version and Download falls back to a plain file download. The download/install sequence needs a real device or CI Gradle build to prove end to end.
- On Android 11 and newer, third-party file managers may need all-files access to browse `Android/data/`; the system Files app can open the folder from Show in Files. The exact path is shown in Settings either way.
- The admin delete lists B2 files through the signer Worker's `/list` endpoint (admin only, paginated, up to 5,000 keys per delete); Firestore data is deleted first, B2 cleanup is best effort.
- Push is a prototype: Android push needs a native FCM setup beyond the web service worker, and the Function sends to all tokens in the room including the sender's own tokens.
- The editor still uses `contentEditable` and raw HTML for note bodies; that was not rebuilt in this test release.
- PWA manifest icons `icon-192.png` and `icon-512.png` are still missing from `client/public/`; add them for install to work properly.
- Web view only: note text does not align with the ruled lines of the page on web. It is correct on mobile, so this is a known web-only cosmetic issue, do not treat it as a blocker.
